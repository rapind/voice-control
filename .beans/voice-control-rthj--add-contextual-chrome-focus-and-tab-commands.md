## Goal

Allow voice control to focus Google Chrome and execute Chrome tab commands using application context.

## Established behavior

- Chrome is the supported browser.
- When Chrome is the active supported application for a voice session, shared aliases such as `focus 1` should execute Chrome behavior rather than Ghostty behavior.
- When Ghostty is the active supported application, the same aliases continue to execute Ghostty behavior.
- A configured global focus alias should be able to bring Chrome forward from another application.
- Voice aliases remain configuration-driven and are never hard-coded.

## Required architecture

The current controller uses `configuration.target`; it does not derive command context from the frontmost application. Add an explicit session target:

1. At wake detection, inspect the frontmost application before changing focus.
2. If it is a supported target, capture its application type and PID for the session.
3. Resolve target-scoped command aliases and keyboard behavior from that captured application type.
4. If the frontmost application is unsupported, fall back to `configuration.target`.
5. Keep direct global application-focus commands separate from target-scoped tab commands.

This prevents the same spoken alias from executing the wrong application's shortcut.

## Native Chrome shortcuts

Chrome already supplies useful macOS shortcuts:

- Command+1 through Command+8 select tabs 1 through 8.
- Command+9 selects the last tab, not necessarily tab 9.
- Command+Shift+] selects the next tab.
- Command+Shift+[ selects the previous tab.
- Command+T creates a new tab.

Custom Chrome mappings are unnecessary for these operations unless exact ninth-tab selection or different semantics are required.

## Decisions still needed

- Whether `focus 9` should preserve Chrome's native last-tab behavior or use Chrome automation for exact ninth-tab selection.
- The configured global alias for bringing Chrome forward, for example `focus chrome` or `focus browser`.
- Whether Chrome new-tab, next-tab, and previous-tab commands belong in the first implementation.

## Acceptance criteria

- A configured global command focuses Chrome from another application.
- Waking while Chrome is frontmost captures Chrome as the session command context.
- Waking while Ghostty is frontmost preserves Ghostty command context.
- `focus 1` through `focus 8` select the corresponding Chrome tabs through native shortcuts.
- `focus 9` behavior is explicitly decided, documented, and tested.
- Chrome aliases load and reload from configuration.
- Unsupported frontmost applications fall back to the configured target.
- Existing Ghostty and ChatGPT behavior remains intact.
- Live smoke tests verify cross-application focus and contextual tab selection.



## Context decision

Shared positional aliases do not need separate implementations for Chrome and Ghostty when their native shortcuts are identical. `focus 1` through `focus 8` may use the same Command+number keystrokes, delivered to the captured frontmost supported application.

Chrome-only aliases must be enabled only when Chrome is the captured session target. For example, a configured `refresh tab` alias may send Command+R in Chrome, but it must not parse or execute while Ghostty is the session target. Ghostty-only aliases follow the same rule in the other direction.

Command parsing therefore uses two groups:

- Shared commands whose keyboard semantics are identical across supported targets.
- Target-scoped commands loaded and matched only for the captured session target.

The app must still capture session context before it focuses or sends keystrokes. Otherwise the current configured-target behavior could bring Ghostty forward and route a shared shortcut there even when Chrome was originally frontmost.
